# 架构待优化

> 已识别但**尚未实施**的架构改进项。每条含「现状 / 问题 / 方案 / 代价 / 状态」。
> 动手前：改前端先读 `docs/前端规则.md` + `docs/设计规范.md`，改后端先读 `backend/README.md`。

## 背景：内容在什么时刻被处理

`content/*.md` 是唯一内容源（git 里的 markdown），但目前**同时被两个消费者以两种时机读取**：

| 消费者 | 读取时机 | 入口 |
|---|---|---|
| 页面展示（博客/笔记/项目） | **运行时** 每次进站拉 JSON | `GET /api/content` → `src/api.js:11` → `useContent()` |
| 首页对话 Agent | **运行时** 语义检索 | `POST /api/chat/stream` → `search_knowledge` 工具 → pgvector |

对比参照（纯静态站的形态）：md 在**构建期**被编译成 HTML 文件，运行时不需要服务端即可读全部内容。
参考实现：`yuanchaofa.com`（Python SSG Apethon）——84 篇文章 = 84 个静态文件 + 39 个标签页 + 16 个分类页，搜索靠一个 32KB 的静态索引 JSON。

**核心判断**：本项目的架构复杂度对**首页 Agent** 是必要的，但对**内容页**是多余的——这部分内容本质上是静态的。

## 待优化 1：内容页去后端化

**优先级**：P0　**状态**：待实施

### 现状（实测）

- 内容页数据全部走运行时接口：`src/pages/BlogPage.jsx:7` / `NotesPage` / `ProjectsPage` → `useContent()`（`src/hooks/useContent.js:13`）→ `fetchContent()`（`src/api.js:14`）
- 后端把 md 实时解析成 JSON：`backend/agent/content.py:31`（`_load_all()` 遍历 `CONTENT_DIR.rglob("*.md")`），出口在 `backend/agent/app.py:65`
- 构建只有 `vite build`（`package.json:8`），**无任何预渲染**；线上首屏 HTML 实测 **592B，body 去标签后为空**（`curl -L https://new-king.com/`）
- 打包产物是纯 SPA，内容靠 JS 运行时渲染

### 问题

1. **静态内容陪绑后端可用性**：后端未启动 / 服务器重启 / `.env` 或数据库隧道失效时，内容页首次进站拿不到数据。注意 `BlogPage.jsx:7` 只解构了 `loading`，**没有 error 分支** —— 失败后 `loading=false` 且 `data=null`，页面会静默渲染成空列表，用户看到"空博客"而不是报错。
2. **SEO 与首屏**：首屏 HTML 无正文，爬虫与不执行 JS 的场景拿不到任何内容。
3. **开发期额外依赖**：本地要看博客页必须同时起 `uvicorn`（`vite.config.js:10` 把 `/api` 代理到 `127.0.0.1:8000`）。

### 方案

**A. 最小改动（建议先做）** —— 构建期把内容导成静态 JSON

- 在构建流程里复用 `content.py` 的解析逻辑，产出 `public/content.json`（或 `dist/content.json`）
- 前端 `fetchContent()` 改为优先读静态 JSON，把 `/api/content` 降级为兜底
- 收益：内容页彻底不依赖后端；改动集中在 `src/api.js` + 一条构建脚本
- 代价：发新文章要重新构建前端（现在部署流程本来就会 build，见 `docs/部署指南.md`）

**B. 完整静态化（后续可选）** —— 每个路由预渲染成 HTML

- 用 Vite 生态的预渲染方案，把 `/`、`/blog`、`/blog/:id`、`/notes/:id`、`/projects/:id` 输出成真实 HTML
- 顺带解决 SEO 与首屏白屏
- ⚠️ **选型前必须先查文档**确认方案维护状态与 Vite 5 / React 18 兼容性，不要凭印象选包（候选包括 `vite-plugin-prerender` 类插件、`react-snap`、或评估迁移到带预渲染的框架）；拿不准时先与维护者确认

### 代价与风险

- 内容与构建产物产生"同步延迟"：静态 JSON 是构建时快照，需确保部署流程里先 build 再上传（现有 Actions 已满足）
- 若保留 A 方案的后端兜底，注意**不要**让缓存层把新旧内容混用（`src/api.js:8` 的模块级 Promise 缓存 + `useContent.js` 注释提到的 localStorage 缓存都要一并核对失效策略）

### 验收

- 停掉 uvicorn，直接 `npm run dev` → `/blog`、`/notes`、`/projects`、详情页均能正常显示
- 线上 `curl -s https://new-king.com/blog | grep <某篇文章标题>` 能命中（B 方案达成）

## 待优化 2：补分类与标签

**优先级**：P2　**状态**：待评估

### 现状

`content/` 下 frontmatter 实测只有这些字段（全量统计 19 篇 md）：

```
title 19 · description 19 · date 19 · url 16 · cover 4 · draft 1
```

**没有 `category` / `tag`**。目前唯一的归类维度是目录：

| 目录 | 类型 | 前端前缀 |
|---|---|---|
| `content/posts/` | 博客 | `/blog` |
| `content/notes/` | 笔记 | `/notes` |
| `content/projects/` | 项目 | `/projects` |

映射关系硬编码在 `backend/agent/content.py:22`（`_TYPE_BY_DIR` / `_ROUTE_BY_DIR`）；前端 8 条路由见 `src/App.jsx:57-65`。**没有聚合页，也没有标签云。**

### 问题

三档目录 = 三个硬编码分类，粒度过粗；同一主题跨 `posts/` 和 `notes/` 的内容无法聚合。

### 方案

1. frontmatter 增加 `tag: []` / `category: ''`，解析逻辑并入 `backend/agent/content.py`
2. 生成 `/tag/:name`、`/category/:name` 聚合页——**用待优化 1 的构建期产物实现，不必新增 API**
3. 标签云上的计数（如 `LLM 23`）在构建期算好写死，不要前端遍历

### 代价

- 需同步扩 `content.py` 的返回结构、前端路由、导航与页面标题
- 新增聚合页会让"发新文章 → 全量重建"的页面数上升

## 待优化 3：关键词搜索与语义检索分流

**优先级**：P1　**状态**：待实施

### 现状

- **站内没有任何搜索入口**：前端 `src/` 全量检索 `tag|category|分类|标签|搜索|search`，唯一命中是 `src/data/mockData.js:203` 的一句打字机演示文案（`{ name: '搜索', ... }`），不是功能
- 唯一的"查找"能力是对话 Agent 的 `search_knowledge` 工具（pgvector 语义检索），走 `POST /api/chat/stream`

### 问题

"找某篇我写过的文章"和"问一个需要跨文档理解的问题"是**两件事**，现在只有后者：

| | 关键词搜索（缺失） | 语义检索（已有） |
|---|---|---|
| 目标 | 找到**哪篇文章** | 回答**一个问题** |
| 技术 | 静态索引 JSON + 客户端匹配 | md 切块 → embedding → pgvector |
| 延迟 | 毫秒级 | 一次 embedding + 向量查询 + LLM 生成 |
| 成本 | 0 | 每次调用计费 |
| 结果 | 确定性 | 概率性，可能漏召回 |

用 Agent 找文章是杀鸡用牛刀：慢、花钱、还可能搜不到。

### 方案

1. **新增纯静态关键词搜索**：构建期导出 `search-index.json`（每篇只存 `title` / `url` / `description` / `tags` / `category` / `date`），首次打开搜索框时 fetch 一次并常驻内存，输入时用 `Array.filter` + `includes()` 匹配，取前 N 条
   - 以当前 19 篇内容的量级，索引体积预计在 10KB 以内，全量遍历是微秒级
   - 可以在首页对话之外单独挂一个搜索入口，两者互不干扰
2. **保留语义检索只服务于对话**：`search_knowledge` 的定位收敛为"回答问题时按需检索"

### 代价与边界

- 静态索引**搜不到正文**（只匹配元数据）；若日后要全文搜索，需换成预构建索引方案（如 Pagefind 类）——同样不需要自建后端
- 索引是构建期快照，须与待优化 1 的重建流程一致

## 附 A：什么时候用哪种形态

| 目标 | 该用 | 本项目现状 |
|---|---|---|
| 内容展示为主，追求速度 / 零运维 / SEO | 纯静态（构建期生成产物） | ❌ 内容页仍走运行时后端 |
| 内容要能被"问"、跨文档推理、交互式 Agent | 运行时后端 + 向量库 | ✅ 这部分必须保留 |
| 两者都要 | **内容页静态化 + 对话服务独立**，别让静态内容陪绑后端可用性 | ← 待优化 1 的目标 |
