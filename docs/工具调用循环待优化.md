# 工具调用循环：标准 loop 对照

> 结论先行：现状是「**单步工具调用**」，不是 agent loop。第二轮脱敏（`_sanitize_messages_for_final`）
> 是为绕开 DeepSeek「上下文里有工具痕迹、但本轮不传 tools → 用文本模拟 `<tool_call>` 导致乱码」的缺陷
> （`chat.py:399-401` 注释，5 次实测 0 乱码）。**这是 workaround，不是规范写法**。
>
> 本文补三件事：标准 loop 的协议细节、脱敏与 loop 的冲突在哪里、按 `AGENTS.md` 的复用守则该用哪个现成组件。
> 与 `docs/工具调用待优化.md` 的「待优化 3 / 4」配套，**不替代**它们（3 管脱敏要不要保留，4 管要不要上 loop）。

## 1. 标准 loop 长什么样

结束权在模型手里：循环到它不再返回 `tool_calls` 为止。

```python
for step in range(MAX_STEPS):          # 兜底，防死循环
    resp = llm_with_tools.invoke(messages)
    if not resp.tool_calls:            # 模型说"我说完了"
        break
    messages.append(resp)              # 一条 AIMessage，带本轮全部 tool_calls
    for tc in resp.tool_calls:
        messages.append(ToolMessage(
            content=TOOLS[tc["name"]].invoke(tc["args"]),
            tool_call_id=tc["id"],
        ))
```

三条协议要点：

1. 结束条件是「模型不再请求工具」，不是代码写死轮数；
2. 一次返回的 N 个 `tool_calls` 必须在**同一条** assistant 消息里，后跟 N 条对应的 `ToolMessage`（这条对应本文件配套的「待优化 2」，现在是拆成 N 条判的）；
3. `MAX_STEPS` 只做兜底（2~3 够用），不是主逻辑。

## 2. 现状与真实动机

| 步骤 | 位置 | 做法 |
|---|---|---|
| 第一轮（非流式） | `chat.py:294` | 拿 `first.tool_calls` |
| 执行工具 | `chat.py:304-393` | 逐个 tool_call 执行，结果 `append` 成 `ToolMessage` |
| 收集引用 | `chat.py:342-344`、`chat.py:390` | 命中块进 `context`，供 `[N]` 引用 / 卡片使用 |
| 脱敏 | `chat.py:402` | 把工具痕迹换成纯文本（定义在 `chat.py:122`） |
| 第二轮（流式，不带 tools） | `chat.py:405` | 一次性生成最终回复 |

脱敏针对的是**模型缺陷**，不是架构偏好：DeepSeek 在「历史里有 tool 痕迹、但这次没传 tools」时会自己用文本模拟
`<tool_call>` 标签，输出乱码。脱干净之后实测修复。

所以判断这件事要不要改，标准只有一个：**DeepSeek 现在还犯不犯这个毛病**，而不是「这样写好不好看」。
同一 prompt 连跑 10 次、看有没有 `<tool_call>` 文本残留在正文里，就能定。这正是「待优化 3」的验收项。

## 3. 脱敏和 loop 是冲突的

loop 的每一步，模型都要**看见上一轮的 tool 结果**（作为 `ToolMessage`）才能决定「还要不要查」。
脱敏把这层信息压成纯文本，模型就失去了「我还可以再查一次」的依据 —— 现在之所以能脱，是因为后面根本没有第二轮决策。

所以顺序是固定的：

1. 先确认 bug 还在不在（待优化 3）；
2. 不在了 → 保留痕迹、第二轮也带 tools，loop 顺手就能做（待优化 4）；
3. 还在 → **不要**在 loop 里每轮脱敏，那会越滚越乱。

### 如果 bug 仍在：可落地的折中

不是「改写 `messages`」，而是「**为最终生成重建一份上下文**」：

- loop 内部全程保留真实的 `AIMessage(tool_calls)` + `ToolMessage`（协议正确、可重放）；
- 最终生成时**新建**一个 prompt：system + 用户问题 + `<doc id="N" title="...">` 包裹的检索结果，**不含任何工具痕迹**；
- `context`（`chat.py:301`）继续维护 `id → chunk` 映射，`[N]` 引用照旧。

这样既不触发文本模拟，也不就地篡改历史 —— 建议先在现有单步结构上验证这一版，再谈 loop。

1. 工具返回值拆成「给人看的文本」+「给前端卡片的结构化 artifact」（现在 `_format_tool_result` 和 `context` 是两套，正好合并）；
2. SSE 的 `tool` 事件挂在每次调用前后，**保持前端协议不变**（形状见「附 A」）。
