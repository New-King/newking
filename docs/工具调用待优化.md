# 工具调用（function calling）待优化

> 结论先行：**协议层是真的 function calling**（模型真的返回结构化 `tool_calls`、参数走 JSON Schema），
> 不规范的是**执行层** —— 目前是「单轮工具 + 手写执行」的简化版，不是标准 agent loop。
>
> 现状来自**读源码**（行号已标），未实跑验证；涉及模型行为的判断来自 `chat.py` 注释里记录的实测。
> 动手前：改后端先读 `backend/README.md`。

---

## 现状：这一轮是怎么跑的

`backend/agent/chat.py:269` 的 `_stream_generator` 就是全部流程：

| 步骤 | 位置 | 做法 |
|---|---|---|
| 绑定工具 | `chat.py:288` | `llm.bind_tools(CHAT_TOOLS)` |
| 第一轮（非流式） | `chat.py:294` | `llm_with_tools.invoke(messages)` → 看 `first.tool_calls` |
| 执行工具 | `chat.py:330`、`chat.py:365` | **不用工具对象**，直接调 `_query_articles_result(args)` / `search(query, top_k=5)`，再 `_format_tool_result()` 拼文本 |
| 回填结果 | `chat.py:326`、`chat.py:355`、`chat.py:361`、`chat.py:392` | 逐个 tool_call 各 append 一条 `AIMessage(tool_calls=[tool_call])` + 一条 `ToolMessage(tool_call_id=...)` |
| 第二轮（流式） | `chat.py:402` → `chat.py:405` | 先 `_sanitize_messages_for_final()` 删掉工具痕迹，再 `llm.stream(final_messages)`（**不带 tools**） |

---

## 判断：哪些是真货，哪些是简化

| 层面 | 是否规范 | 依据 |
|---|---|---|
| 协议 | ✅ 真 function calling | 模型返回结构化 `tool_calls`，非文本模拟 |
| 参数校验 | ✅ 生效 | `@tool` 的 type hints + docstring 生成 JSON Schema（`chat.py:231`、`chat.py:242`） |
| 执行 | ⚠️ 手写 | 工具对象从未 `invoke()`，执行逻辑另写一份 |
| 消息构造 | ⚠️ 简化 | 多个 tool_call 拆成多条 `AIMessage` |
| 上下文传递 | ⚠️ 非常规 | 第二轮删掉工具痕迹（`chat.py:122`） |
| 循环 | ❌ 没有 | 只有「一轮工具 → 一次生成」，模型无法二次检索 |

## 待优化 1：工具「声明」与「执行」两处维护

**优先级**：P1　**状态**：待实施

### 现状

`search_knowledge`（`chat.py:232`）与 `query_articles`（`chat.py:243`）只用来给模型看接口，
真正的执行在循环里另写了一遍：`chat.py:330`（`_query_articles_result`，定义在 `chat.py:159`）与
`chat.py:365`（`search(...)` + `_format_tool_result()`，定义在 `chat.py:99`）。

### 问题

同一份检索逻辑存在两个入口：**改一处忘另一处就会漂移**（比如工具 docstring 描述与真实行为不一致，
或参数在一边允许、另一边没处理）。`AGENTS.md` 的「禁止重复造轮子」守则鼓励复用组件，这里恰好绕开了自家组件。

### 方案

1. 建 `CHAT_TOOLS_BY_NAME = {t.name: t for t in CHAT_TOOLS}`，循环里统一 `tool.invoke(args)`
2. 保留 SSE 卡片：`yield _sse({"type": "tool", ...})` 放在 `invoke()` 前后即可，不影响
3. 结构化数据（前端卡片要的 `url/title/doc_id`）走 **tool artifact**（`response_format="content_and_artifact"`）
   或让工具返回可解析的 JSON 字符串，别只返回人类可读文本

### 代价

- 需重新定义「工具返回值」的格式（现在是拼好的纯文本），`_format_tool_result` 的调用点要挪进工具内部
- 同名工具去重 / 关键词合并（`chat.py:314`）这套逻辑要重新落位

### 验收

- 删掉循环里的手写执行分支后，`search_knowledge` / `query_articles` 仍能出卡片、仍能带回 `context`
- 工具函数体内改一行，行为立刻生效（不再需要改两处）

## 待优化 2：多个 tool_calls 拆成了多条 AIMessage

**优先级**：P1　**状态**：待实施

### 现状

`chat.py:326`、`chat.py:355`、`chat.py:361`、`chat.py:392` 四处都是这个写法：

```python
messages.append(AIMessage(content=first.content or "", tool_calls=[tool_call]))
messages.append(ToolMessage(content=tool_result, tool_call_id=tool_id))
```

即：模型一次返回 N 个 tool_call，就被拆成 N 条「各带 1 个 tool_call」的 AIMessage。

### 问题

OpenAI 兼容协议的约定是：**一条** assistant 消息带**全部** `tool_calls`，随后跟 N 条对应的 `ToolMessage`。
拆成多条虽然本地能跑（DeepSeek 校验宽松），但对严格校验的服务端 / 未来换模型是个隐患。

### 方案

循环只负责**收集**结果，循环结束后一次性组装：

```python
messages.append(AIMessage(content=first.content or "", tool_calls=first.tool_calls))
for tool_call, result, ok in collected:
    messages.append(ToolMessage(content=result, tool_call_id=tool_call["id"]))
```

### 代价

- 循环里目前「边执行边 append」的顺序要改成「先收集再落盘」，SSE 卡片事件不受影响
- 未知工具 / 同名合并的占位回填（`chat.py:327`、`chat.py:362`）也要一并收进收集列表

### 验收

- 让模型一次触发两个工具（如同时问「文章清单 + 检索」），`messages` 里只有一条带 2 个 tool_calls 的 AIMessage

## 待优化 3：第二轮删掉工具痕迹（`_sanitize_messages_for_final`）

**优先级**：P2　**状态**：待评估（**当前是有意为之，别直接删**）

### 现状

`chat.py:402` 调 `_sanitize_messages_for_final()`（定义在 `chat.py:122`），把第一轮的
`AIMessage(tool_calls)` 换成纯文本、把 `ToolMessage` 摘出来拼进正文，然后 `chat.py:405` 用
**不带 tools** 的 `llm.stream()` 生成最终回答。

### 问题

标准做法是**保留** `AIMessage(tool_calls)` + `ToolMessage` 原样发回，并**继续带 tools**，直到模型不再请求工具。
现在是反过来的：刻意让模型「忘了自己有工具」。

### 为什么现在这么写（`chat.py:122` 注释记录的实测）

DeepSeek 在「上下文里出现过工具、但本轮没传 tools」时，会用**文本**模拟 `<tool_call>` 标签 → 输出乱码。
剥掉工具痕迹后实测 5 次 0 乱码。**这是绕模型缺陷的 workaround，不是规范写法。**

### 方案（先验证再动）

1. 先确认 DeepSeek 当前版本是否仍会文本模拟（同一 prompt 跑 5~10 次）
2. 若已修复：改成「保留痕迹 + 第二轮也带 tools」，此时待优化 4 的循环顺手就能做
3. 若未修复：保持现状，但把「为什么这么写」升级成硬约束写进 `backend/README.md`（现在只在代码注释里）

### 代价

- 改错会直接让回答出现乱码，属于**用户可见的质量回退**，必须 A/B 对比后再定
- 与待优化 4 强耦合：这一层不放开，就没有真正的多轮工具循环

### 验收

- 连续 20 次对话（含「先问清单、再追问细节」的多轮场景）无 `<tool_call>` 乱码

## 待优化 4：没有 agent loop（模型不能二次检索）

**优先级**：P3　**状态**：待评估

### 现状

`_stream_generator` 结构固定：一轮 `invoke`（带工具）→ 一轮 `stream`（不带工具）。
模型若觉得第一次检索结果不够，**没有第二次机会**。

### 问题

复杂问题（「对比我写过的两篇 RAG 文章，谁讲的切块更细」）可能一次检索召回不全，
标准 agent loop 靠「模型再请求一次工具」补召回，现在直接进终局生成。

### 方案

改成 `while` 循环 + 最大步数上限（如 5），条件是「模型不再返回 tool_calls」。
放在 LangChain 里就是手写一个 while；放在 LangGraph 里就是条件边回环 + `recursionLimit`（见附 B）。

### 代价

- 每多一轮 = 多一次模型调用（延迟 + 费用），必须设步数上限
- SSE 卡片要改成「每轮追加一组」，前端渲染逻辑要跟着调（**这正是「界面可能要改」的接口点**）

### 验收

- 构造一个需要两次检索的问题，能看到两轮工具卡片且最终回答引用了两轮结果

## 附 A：与界面改动的关系（改 UI 前先看这条）

SSE 的事件形状是**手写流程的产物**，不是框架给的：

| 事件 | 产生位置 | 前端用途 |
|---|---|---|
| `{"type": "tool", "name", "status", "related"}` | `chat.py:333`、`chat.py:367` 等 | 检索进度卡片、相关文章 |
| `{"type": "thinking", ...}` | `chat.py:279` | 思考态 |
| `content` 结构化（`url/title/doc_id`） | `chat.py:390` 的 `context` | `[N]` 引用 → 链接块 |
| `{"type": "done"}` | 生成结束 | 收尾 |

结论：**界面（卡片/引用）和「工具怎么执行」是绑在一起的**。
若先改界面、之后再动待优化 1/2/4，卡片事件要重新映射一次。建议顺序：**先定这一层要不要改，再改界面**。

## 附 B：什么时候才需要上 LangGraph

**结论：现在不需要。** 当前是「路由 → 检索 → 流式输出」的线性链路，四类需求全都不占：

| LangGraph 解决的 | 本项目现状 |
|---|---|
| 循环 / 分支 / 并行（多步 agent） | 一轮工具调用即结束 |
| 持久化记忆（checkpointer + thread） | `history` 由前端传入 |
| 人工介入（`interrupt` 审批） | 无写操作需要审批 |
| 断点续跑 / 重放 / 节点级追踪 | LangSmith 看链路已够 |

**触发条件**（出现任意一条再考虑）：

- 需要真正的多轮工具循环（即待优化 4）
- 要加后台写操作 + 人工确认
- 要跨会话记忆 / 对话续跑
- 要把流程可视化给非开发者看

**低成本路径**：先只把 LangGraph **当库用**（后端内 `graph.invoke`，保留 FastAPI 与现有 SSE），
不上 Agent Server；等确实需要 `useStream` 或平台能力（Studio / 部署托管）再换。
