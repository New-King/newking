- 定位：检索怎么实现、查不查、查完怎么筛。这一层跟用哪个框架无关，换库也是同一套取舍。

## 最朴素：每次都查

不管问什么都先检索，取前 k 条（k 一般 4–10），全部塞进 prompt，靠提示词兜底：

```text
资料无关就忽略；资料里没有就说不知道。
```

一次模型调用，链路最短。缺点是无关内容白占 token，模型也未必真听话 —— 噪声多的时候照样会硬引。

## 「没召回就跳过」这个判断不成立

向量检索永远返回前 k 条，按距离排序，哪怕全是垃圾也会填满。

所以「召回数量为 0」几乎不会发生，拿条数做开关没意义。要看的是**分数**，不是条数。

## 主力方案：多取 + 阈值砍 + 重排

```python
index.as_query_engine(
    similarity_top_k=10,                      # 先多取
    node_postprocessors=[
        SimilarityPostprocessor(similarity_cutoff=0.6),  # 再按分数砍
    ],
)
```

- 只保留分数达标的块，剩下的不进 prompt
- 想要更准就再叠 `LLMRerank(top_n=3)`
- 阈值太高会误杀正常内容，太低等于没筛 —— 拿一批真实问题跑一遍，看分数落在什么区间，再定这条线

## 真需要判断层时的几种做法

| 方案 | 怎么做 | 代价 |
|---|---|---|
| tool 调用 | 把检索包成工具，模型自己决定调不调 | 多一轮模型调用 |
| 路由器 | 选择器挑走哪个引擎（`RouterQueryEngine`） | 多一次小模型调用 |
| 前置分类器 | 一次 prompt 输出「要不要查库」 | 便宜、可控 |
| 关键词规则 | 命中特定词才查 | 零成本、最土 |

演变过程：2023–2024 主流是路由器 + 选择器，因为当时 function calling 不稳，只能先显式分类再路由；现在工具调用可靠了，需要判断时更偏向 tool calling。

## 检索怎么算：暴力 vs 索引

找「余弦最大的 k 条」这个目标不变，差别只在**算几条**：

| | 暴力（flat） | ANN 索引（HNSW / IVF） |
|---|---|---|
| 算多少条 | 全部 N 条 | 剪枝后几十~几百条 |
| 结果 | 精确，召回 100% | 近似，通常 ≥95% |
| 适合 | < 1 万条 | 1 万以上 |

小规模下索引反而更慢：省的计算本来不多（`log 300 ≈ 8` 体现不出来），而图遍历是随机访存，一次 cache miss ≈ 100 次顺序乘加；还要摊建索引成本、调 `efSearch`/`nprobe`、维护索引与主表一致。跟「小表不用索引」是同一条规律。

只写一行代码就想提速的三处：向量存 BLOB（float32）而不是 JSON 文本；存归一化向量，余弦退化成点积，省两次开方；只取 `id + 向量` 两列，别 `SELECT *`。

## 门控兜底 ≠ 并行融合

标准的混合检索是两路都跑、RRF 合并（见 Memory 那篇）。另一种省事的写法是**门控**：关键词先跑，命中不足 n 个才走向量。

代价很硬：关键词命中 3 条错的，向量再准也进不来。只在「精确查询占绝大多数、想省一次嵌入请求」时才划算。

## 检索单元决定叫什么

- chunk-level：文档切块，一条向量一段文本 → 这才是通常说的 RAG
- entity-level：一个实体一条向量（一个人、一个商品），不经切块
- agentic retrieval：检索包成工具，模型自己决定调哪个，而非固定 pipeline

实体 + 工具检索 + 关键词/向量两路，组合起来叫 **agentic hybrid retrieval**，跟「文档 RAG」不是同一个形状，别混标。

## 结论

- 语料集中、问题基本都在范围内 → 固定检索 + 阈值，别提前加判断层
- 问题域杂（闲聊 / 业务查询 / 文档问答混在一起）→ 再加分类器或 tool
- 「要不要检索」这一步，多数项目根本不需要，先把阈值和重排调好比什么都值
- 数据不到万级就别上向量库，全表算余弦就是正解；要提升排序质量，先换 BM25（SQLite FTS5 自带）比重排更划算
