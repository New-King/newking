- 定位：给agent的稳定性、回复准确性做一系列单元测试、得分评估、线上指标。
- 测试框架：pytest、Jest、Vitest


**高频三问：**

1. 你怎么评估 agent 好不好？
   用户角度：UI 友好度、能不能解决实际问题、收费 / 速度。
   技术角度：三层 —— 单元（CI 查不变量，只判过 / 不过）、任务（评测集通过率）、线上（真实流量指标）。三层缺一层都答不完整。

2. 上线后怎么知道变差了？
   一般直接接 LangSmith / LangFuse，trace、报错、成本、延迟都自动收，不用自己埋点。
   盯几个数：报错率、平均步数、成本、没给出结果的次数。哪个掉了就去看那一次的 trace。
   数据不能外传才自己写日志（Hermes 就是这种），代价是要自己搭报表。

3. 一次失败的 run 你怎么查？
   先分两类：过程失败、质量失败，查法完全不同。
   · 过程失败（trace 里有信号）：工具调错 / 上下文被截断 / 步数耗尽 / 接口报错
     按 trace 看三件事：工具选对没、上下文爆没、预算用完没，哪里不对就是哪里。
   · 质量失败（trace 里没信号）：回复正常返回，但答偏、含糊、漏关键点
     ① 发现：用户反馈（👎 带原因 + session_id）或人工抽检，先把案例捞出来
        - 再按原因分类（答偏 / 漏关键信息 / 答非所问），定位到底哪类场景差
     ② 盯住：把案例做成评测集，每次改动跑一遍看通过率，掉了就是改坏了
        - 用例长这样：问「我的订单到哪了」，检查三样 —— 工具调用、循环次数、最终答案
   一句话：trace 是排障工具，不是质量评估工具。

4. 如何进行 agent 测评？

   **相关工具（各管一段）**
   · pytest / Vitest —— 写断言，批量跑用例，出通过/失败报告（单测）
   · LangSmith —— 建题库（Dataset）、跑实验对比（Experiment）、看 trace、人工标注队列
   · LangFuse / Phoenix —— 线上 trace、成本、延迟监控
   · RAGAS —— RAG 两段指标（faithfulness、context precision / recall），LLM 当裁判
   · DeepEval —— LLM 裁判类指标，写法接近 pytest，RAG 和 agent 都能用

   ① 先明确评谁（题目怎么出）
   · Agent：任务 + 期望的最终结果（可选：期望调用哪些工具，兼容 RAG 类型的 agent）
   · RAG：问题 + 该命中哪些块/文件 + 参考答案

   ② 判分手段：能断言的先断言，判不了的才调模型
   · 断言测试（不花钱、结果确定）：输出结构、工具参数、步数、内容值（有没有包含 xxx）
   · LLM 当裁判 / 人工抽检：主观质量（答得好不好），断言覆盖不到

   ③ 看哪几个数
   · 端到端成功率 —— 一批任务跑完的完成率，主指标
   · 轨迹 —— 工具调用顺序、调用次数、有没有绕路
   · 成本与延迟 —— token 开销、耗时、稳定性

   ④ RAG 分两段看，才知道是谁的问题
   · 检索段：该召回的块有没有被召回（hit_rate、mrr、context recall）
   · 生成段：答案有没有编造、是否切题（faithfulness、answer relevancy）
   · 检索没中就别怪模型；两项都高但答案仍错，才是生成或提示词的问题
